## Problems Encountered & Solutions

### 1. Ship Library Showing Only 3 Ships (Not 40)

**Symptom:** After deploying the updated library, only 3 ships appeared in the UI. The `data/all_ships.json` had 40 ships, but the app refused to load them.

**Root Cause:** `loadDefaultShips()` in `tableStore.ts` had an early-return guard:
```typescript
if (state.ships.length > 0) return; // Don't overwrite existing library
```
Since Zustand's `persist` middleware saves ships to `localStorage`, any previously saved ships (even 3) blocked loading the new 40-ship library entirely.

**Solution:** Removed the early return. The function now always fetches `all_ships.json` and merges new ships by ID, preserving existing user ships while adding new defaults:
```typescript
const existing = state.ships.find((s) => s.id === ship.id);
if (!existing) state.ships.push(ship);
```

### 2. Forgejo Pages White Screen

**Symptom:** `https://pages.gi7b.org/gi7b/ce-shipgen` showed a blank white page. Local dev server worked fine.

**Root Cause:** `ronmi/forgejo-pages` serves all files via Forgejo raw API, which returns `Content-Type: text/plain` for every file. Browsers with `X-Content-Type-Options: nosniff` block `<script>` and `<link rel="stylesheet">` tags that get `text/plain`, so the React app never mounted.

**Solution:** Inline all CSS and JS into `index.html` before deploying. The `assets/` folder (external `.js`/`.css`) is stripped from the `static-pages` branch. Created `scripts/deploy.mjs` to automate build → inline → push.

### 3. Deploy Branch Polluted with node_modules

**Symptom:** `static-pages` branch grew to 20,000+ files and 100MB+ due to `node_modules/` being committed.

**Root Cause:** Manual deploy used `git add -A` on the `static-pages` branch without a `.gitignore`. When switching from `main` (which has `node_modules/` in `.gitignore`) to `static-pages` (orphan branch, no `.gitignore`), the working directory's `node_modules/` got committed.

**Solution:** Added `.gitignore` to `static-pages` branch. Updated deploy script to explicitly delete everything except `.git` and `.gitignore` before copying the new build. Deploy SOP now includes verification: `git ls-tree --name-only static-pages`.

### 4. Stale Data Deployed

**Symptom:** Updated `public/data/all_ships.json` but deployed site showed old data.

**Root Cause:** Copied the existing `dist/` folder to `static-pages` without rebuilding after the data update. The `dist/` folder was built *before* the data change.

**Solution:** Deploy SOP now enforces: `npm run build` must be the **first** step, run **after** all source/data changes are finalized.

### 5. Filter Panel Not Working in ShipDesigner "Load from Library"

**Symptom:** The TL, Tag, and Min-Max DT filters worked on the main Ship Library page but not on the ShipDesigner's "Load from Library" dropdown/sidebar.

**Status:** Partially fixed — filters added to ShipDesigner but the selection list below the sheet may still not filter correctly. Remaining work: ensure `filteredLibraryShips` memo is applied to both the dropdown and the quick-list sidebar in ShipDesigner.

## Key Architectural Lesson: Taxonomy Strategy & Rule Creation

### The Core Insight

**Every ship in the library must be describable by a set of deterministic rules derived from canonical reference tables.** This is not just about storing ships — it's about creating a *taxonomy* where any ship can be validated, corrected, and even generated from first principles.

### Method: Analyze → Pattern → Rule → Predict

1. **Analyze with Examples:** Start with raw data (Excel sheets, SRD formulas). Extract every ship manually. Note discrepancies, edge cases, and inconsistencies.
2. **Seek Patterns:** Group ships by role, size, TL. Notice that "Fighter" always has certain traits. "Passenger Liner" always has others. Identify the *dimensions* that define a ship class.
3. **Develop Rules:** Encode the patterns into deterministic rules. Rules should be *close enough* to cover 90%+ of cases, with manual overrides for the exceptions.
4. **Predict & Validate:** Use the rules to classify existing ships, generate new ones, and audit the library against the tables.

### Iron Triangle Classification (S/A/P)

Applied this method to create the Iron Triangle classifier:

| Dimension | Meaning | Calculation |
|---|---|---|
| **S** — Structural | Hull, armor, drives, power, bridge | Sum of structural component dtons |
| **A** — Arsenal | Weapons, military modules | Sum of weapon/military module dtons + cost |
| **P** — Payload | Cargo, passengers, crew amenities, non-military modules | Everything else |

From S/A/P ratios, derive:
- **Role:** Vanguard (high A), Skirmisher (balanced), Hauler (high P)
- **Size Class:** Craft, Small Ship, Medium Ship, Line Ship
- **Class Name:** e.g., "Bulk Transport", "Cutter", "Monitor"

This is the **Taxonomy** — a hierarchical classification system that gives every ship a semantic identity beyond just stats.

### Tagging Rules

Auto-tags derived from ship names and hull size:
```
 civilian  → yacht, liner, trader, merchant, passenger, courier, research, survey, exploration, mining, tender, habitat, shuttle, boat
 warship   → fighter, frigate, corvette, destroyer, patrol, defense boat, raider, military, escort
 small-craft → hull ≤ 100 DT
 merchant  → trader, merchant, freighter
 passenger → liner, passenger
 military  → fighter, frigate, corvette, destroyer, patrol, defense boat, raider, military
 exploration → exploration, survey, research
 mining    → miner, mining
```

With conflict resolution: if a ship matches both `civilian` and `warship` (e.g., "Escort Frigate"), warship wins.

## Audit System: Tables as the Source of Truth

### The Problem

The library stored ship stats as **line-item totals** (e.g., "125 Stateroom" = 125 DT, 1 entry with qty=1). But the reference tables store **per-unit values** (e.g., 1 Stateroom = 1 DT). When the tables were updated, the library had no way to know if its stored totals were still correct.

### The Solution: Table-Driven Audit

Created `src/utils/shipAuditor.ts` that:

1. **Re-computes** every line item from reference tables:
   - Life support: lookup by `facilityType` in `life_support.json`
   - Modules: lookup by name in `ship_modules.json`
   - Weapons: lookup by name in `ship_weapons.json`
   - Supplies: lookup by name in `ship_supplies.json`
   - Vehicles: lookup by name in `ship_vehicles.json`

2. **Compares** stored values vs table values:
   ```
   stored_dtons  vs  table_dtons × qty
   stored_cost   vs  table_cost × qty
   ```

3. **Flags violations** by severity:
   - **Critical:** >10% delta, or zero when should be non-zero
   - **Warning:** Any mismatch
   - **Info:** Minor discrepancies

4. **Auto-corrects:** `correctShip()` returns a new ship with all values updated from tables, then `updateShip()` replaces the old one.

### Key Data Structure Convention

```typescript
// Reference tables store PER-UNIT values
{ name: "Stateroom", dtons: 1, cost: 50000 }

// Ship modules[] store PER-UNIT with qty
{ module: "Stateroom", dtons: 1, cost: 50000, qty: 125 }

// Ship components[] store LINE TOTALS with qty=1
{ section: "Life Support", module: "125 Stateroom", dtons: 125, cost: 6250000, qty: 1 }
```

The audit compares:
- `modules[]` per-unit × qty against tables
- `components[]` totals against (table per-unit × qty)

This separation allows the BOQ to show clean totals while the audit validates against canonical per-unit values.

### Audit Results (v0.09)

- **32 ships** pass audit clean
- **8 ships** have warnings (custom bay modules not in tables — e.g., "20DT Launch Bay")
- **0 critical** violations after reconciliation

## Ship Library Storage Model

### Where Quantities Are Kept

| Field | Stores | Example |
|---|---|---|
| `modules[]` | Per-unit dtons/cost with `qty` | `{module:"Stateroom", dtons:1, cost:50000, qty:125}` |
| `weapons[]` | Per-unit dtons/cost with `qty` | `{name:"Pulse Laser", dtons:1, cost:100000, qty:6}` |
| `lifeSupport[]` | Per-unit dtons/cost with `qty` | `{facilityType:"Stateroom", dtons:1, cost:50000, qty:125}` |
| `components[]` | **Line totals** with `qty:1` | `{section:"Life Support", module:"125 Stateroom", dtons:125, cost:6250000, qty:1}` |
| `cargo` | Computed remainder | `hullDtons - sum(all_allocated_dtons)` |
| `availableDtons` | Hull minus everything | `hullDtons - structural - weapons - modules - cargo` |

### Normalization Rules

1. All `components[]` entries use `qty: 1` with totals in `dtons`
2. Life support names include counts: `"125 Stateroom"`, `"2 Low Berth"`, `"10 Emergency Low Berth"`
3. Emergency Low Berth is distinct from Low Berth: 0.25 DT/25K Cr vs 0.5 DT/50K Cr
4. Cargo is always computed as remainder, never extracted from Excel
5. `availableDtons = hullDtons - all_allocated` (not just structural)

## The Batch Traits Mechanic (Future Work)

### The Concept

Real-world engineering execution varies by manufacturer, nation, and era. Two ships with the *same fundamental design* (same hull, same drives, same blueprint) can have different performance due to:

- Manufacturing tolerances
- Material sourcing differences
- National engineering traditions
- Cost-cutting vs. over-engineering

**Batch Traits** model this variation as modifiers applied to a base design:

```
Base Design: TL9 Patrol Frigate, 300 DT
├─ Batch: Indian Navy (-3% mass on all components, +2% fuel consumption)
├─ Batch: Chinese PLA (-5% cost, -5% armor rating)
├─ Batch: USAF (+5% thrust impulse, +10% cost)
├─ Batch: European Union (+3% sensor range, +2% computer rating)
└─ Batch: Refit 2615 (+8% mass from added armor, updated software)
```

### Trait Categories

| Category | Example Modifiers |
|---|---|
| **Mass** | ±2-5% component mass (lighter composites vs. heavier steel) |
| **Cost** | ±5-10% total cost (mass production vs. boutique) |
| **Thrust** | ±5% impulse (engine tuning, nozzle design) |
| **Armor** | ±5% effective rating (heat treatment quality) |
| **Sensors** | ±3% range (electronics quality) |
| **Fuel** | ±2% consumption (combustion efficiency) |
| **Reliability** | ±10% maintenance interval (workmanship) |

### Application to Mneme & FreeCAD

This mechanic bridges the gap between:
- **CE ShipGen** (theoretical design from tables)
- **Mneme Space Combat** (operational performance in scenarios)
- **FreeCAD** (physical 3D models with actual mass properties)

A ship designed in CE ShipGen gets its *base stats* from the SRD tables. Batch Traits modify those stats for a specific faction or manufacturer. The FreeCAD model uses the *actual mass* from the Batch Trait to compute center of gravity, moment of inertia, and structural loads. Mneme combat uses the *modified thrust and armor* for engagement calculations.

**The Taxonomy + Rules + Batch Traits pipeline:**
1. **Taxonomy** defines what the ship IS (role, size, class)
2. **Rules** define what it MUST have (components, quantities, costs)
3. **Audit** validates that it matches the canonical tables
4. **Batch Traits** define how a specific execution DIFFERS from the ideal
